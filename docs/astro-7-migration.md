### Результат замера 1: entry.id

`generateIdDefault` в `astro/dist/content/loaders/glob.js:9-20` вызывает ту же
`getContentEntryIdAndSlug`, что и легаси-коллекции, с `contentDir: base`. Форма id
совпала со старым slug. Плюс `src/lib/blog.ts` всё равно сводит его к последнему
сегменту. **URL ни одного из 318 постов не изменился.**

### Результат замера 2: MessageChannel — плагин НЕСУЩИЙ

Проверено запуском воркера без полифила:

```
Uncaught ReferenceError: MessageChannel is not defined
  at requireReactDomServer_browser_production
  at chunks/_@astro-renderers_Bhz6Cwgb.mjs
```

Причина: `dist/_worker.js/index.js` статически импортирует чанк рендереров, а
`react-dom/server` делает `new MessageChannel()` на верхнем уровне модуля **без**
`typeof`-охраны. Воркер не стартует вообще — падают все SSR-маршруты, не только React.

Отдельно проверено: **`nodejs_compat` эту дыру не закрывает** (флаг включался, ошибка
та же). Полифил удалять нельзя.

Плагин переписан: матчит чанки по `new MessageChannel`, а не по имени
`_@astro-renderers_`. Теперь переименование чанка в Astro 6/7 его не сломает. Клиентская
сборка исключена через `this.environment?.name === "client"`.

### Побочная находка: нестабильная сортировка (исправлено)

Шесть мест в `src/lib/blog.ts` сортировали по дате без тай-брейка. При равных
`publishedAt` порядок зависел от порядка обхода лоадера. Замер показал: посты **реально
переезжали между страницами пагинации 5 и 6**. Баг существовал и до миграции — она его
лишь проявила. Добавлен общий компаратор `byPublishedDesc` с тай-брейком по slug; такой
же тай-брейк добавлен в `scripts/build-cache.mjs`. Две подряд сборки теперь дают 0
расхождений в 474 HTML-файлах.

### Побочная находка: `markdown:` в конфиге коллекции был мёртвым

Блок `markdown: { remarkPlugins, rehypePlugins }` не входит в тип конфига коллекции и
молча игнорировался. Доказательство: класс `heading-anchor` из
`rehype-autolink-headings` встречается в собранном сайте **0 раз**. Якоря заголовков
генерирует встроенный механизм Astro. Три пакета удалены как неиспользуемые.

**Это снимает главный риск Фазы 2**: проект не зависит ни от одного remark/rehype-плагина,
поэтому переход на Sätteri в Astro 7 больше не «высокий риск на 318 файлах». Остаётся
проверить только, что Sätteri генерирует те же id заголовков.

### Побочная находка: `npm run preview` не работает

`astro preview` не поддерживается адаптером Cloudflare — команда падает, хотя описана в
CLAUDE.md как рабочая. Локальный прогон делается через
`npx wrangler pages dev dist`; конфиг добавлен в `.claude/launch.json`.

### Ещё не сделано

Бампы версий (Astro 6, затем 7), Zod 4, i18n `redirectToDefaultLocale`, session-драйвер,
`ViewTransitions` → `ClientRouter`, Node в CI. См. фазы ниже.

## 0. Срочность: не срочно

**Изначальная гипотеза была неверна.** Я аргументировал спешку тем, что в Astro <7 есть
Host-header SSRF в fetch'е prerendered-страницы ошибки (`GHSA-2pvr-wf23-7pc7`). Проверка
адвайзори это опровергла: **`@astrojs/cloudflare` в списке НЕ затронутых** — дыра касается
`createRequestFromNodeRequest` из `astro/app/node` и сторонних адаптеров.

Остальные адвайзори Astro — XSS, и все требуют, чтобы во вредный сток попал управляемый
атакующим ввод. Проверено по коду:

| Сток из адвайзори | Есть в проекте? |
|---|---|
| `define:vars` | нет |
| spread-пропсы `{...attrs}` | нет |
| динамические `transition:*` | нет |
| server islands (`server:defer`) | нет |
| динамические имена слотов | нет |
| `set:html` | 9 мест — **все со статикой** (словари переводов, SVG-константы, JSON-LD из метаданных постов, статический 404) |

Единственный пользовательский ввод — поисковый запрос — обрабатывается клиентским React
через Algolia; страница поиска prerendered и не читает query-параметры на сервере.

**Вывод:** практический runtime-риск ≈ 0. Мигрировать надо, но по календарю обслуживания,
а не пожарным порядком.

Что всё-таки толкает сделать это в обозримом будущем:

- Astro 5 перестанет получать фиксы; отставание на два мажора со временем только дорожает.
- `npm audit` останется красным (9 записей). Постоянный красный аудит — шум, который
  замаскирует настоящую проблему, когда она появится.

## 2. Ключевая развилка: markdown в Astro 7

Самый дорогой пункт — 318 MDX-файлов проходят через **другой процессор**.

`@astrojs/mdx@7` имеет peer-зависимость `@astrojs/markdown-satteri@^0.3.1`. Проект
использует `remark-gfm`, `rehype-slug`, `rehype-autolink-headings`
(`src/content/config.ts:74-86`), причём autolink-headings формирует якоря заголовков —
это **живые URL с якорями**, их регрессия видна в SEO.

Два пути на шаге 6→7:

- **A (рекомендую): оставить remark** — переустановить `@astrojs/markdown-remark` и задать
  его процессором. Сохраняет три плагина и текущий HTML заголовков. Дешёвый и обратимый.
- **B: портировать на Sätteri** — «правильнее» вдолгую, но требует найти аналоги трёх
  плагинов и заново проверить якоря на 318 файлах.

Делать B, если вообще, — **отдельной задачей после** того, как миграция уже зелёная.

## 4. Оценка объёма

Это **суждение**, а не замер — реальных данных о скорости на этом коде у меня нет:

- Фаза 1 — самая дорогая: контент-слой + Zod + плагин Vite.
- Фаза 2 — дешевле, если идти путём A по markdown.
- Наибольшая неопределённость: форма `entry.id` (может задеть URL всех постов) и
  плагин MessageChannel (может дать тихий рантайм-отказ, невидимый на сборке).

Обе неопределённости снимаются **замером в первый час работы** — начинать надо с них,
а не с механических бампов.
